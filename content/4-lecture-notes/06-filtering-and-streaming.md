> [!abstract] In one breath
> Earlier randomized structures are always right and probably fast; these are always fast and probably right, with an error probability $\delta$ chosen in advance. A **Bloom filter** stores $n$ items in $m$ bits by setting $k$ hashed bits per item; a query answers "no" if one of its $k$ bits is 0 — always correct — and "maybe" otherwise, wrongly with probability about $(1 - e^{-kn/m})^k$. With the best $k = (m/n)\ln 2$, a rate $\delta$ costs about $1.44\lg(1/\delta)$ bits per item. A **streaming algorithm** reads a huge sequence once, with time per item and memory independent of its length; the **count-min sketch**, $\lceil\ln(1/\delta)\rceil$ rows of $\lceil e/\varepsilon\rceil$ counters, estimates how often an item has occurred, never too low and more than $\varepsilon N$ too high with probability at most $\delta$. The section on counting distinct items is unfinished.

> [!note] Where this fits
> A continuation of [[4-lecture-notes/05-hashing|note 5]]: both structures are hash tables that throw away the keys, analyzed with the universal and 2-uniform families of [[4-lecture-notes/05-hashing#53-but-not-too-random|§5.3]] and with Markov's inequality and Chernoff bounds from [[4-lecture-notes/04-tail-inequalities|note 4]] ([[concepts/tail-inequalities]]). The streaming model is the model of a DFA — one left-to-right pass with little memory ([[1-models-of-computation/03-finite-state-machines#31-intuition-a-dfa-is-a-loop-with-constant-memory|Models of Computation §3.1]]) — relaxed to memory that may grow slowly and answers that are approximate, and correct only with high probability. **Not assigned in CS 374 this semester; CS 473 material at Illinois.**

The note's opening fixes the trade-off: an **error rate** $\delta$, and the resources needed to be correct with probability $1-\delta$; "with high probability" means $\delta < 1/n^c$, but a small constant such as $1/1000$ is often enough in practice.

## 6.1 Bloom filters

A **Bloom filter** (Burton Bloom, 1970; earlier, as Zatocoding, Calvin Mooers, 1947) represents a set $X$ of $n$ items from a universe $\mathcal U$ in very little space, at the price of **false positives**: it may report $y\in X$ when $y\notin X$, never the reverse — useless as an exact dictionary, useful as a cheap filter in front of a slower exact structure.

It is an array $B[0\,..\,m-1]$ of bits and $k$ hash functions $h_1,\ldots,h_k\colon\mathcal U\to[m]$. **What is random:** the analysis assumes the $h_j$ are independent ideal random functions — unrealistic, and nobody knows whether limited independence suffices here, but real filters behave as predicted.

```text
MakeBloomFilter(X):                     BloomMembership(B, y):
    for h ← 0 to m − 1                      for j ← 1 to k
        B[h] ← 0                                if B[h_j(y)] = 0
    for i ← 1 to n                                  return False
        for j ← 1 to k                      return Maybe
            B[h_j(x_i)] ← 1
```

Building takes $O(m + kn)$ time, a query $O(k)$. **No false negatives:** a member's bits were set at its insertion and are never cleared. A non-member gets Maybe exactly when all $k$ of its bits were set by other items.

## 6.2 False positive rate

Each of the $kn$ hash values $h_j(x_i)$ is uniform on $[m]$, so a fixed bit is still 0 after the construction with probability
$$
\Pr[B[h] = 0] = \Big(1 - \frac1m\Big)^{kn}\approx e^{-kn/m} =: p .
$$
The number of 0-bits is close to its mean $mp$ with very high probability (a Chernoff bound), and a query $y\notin X$ probes $k$ independent random bits, so the false-positive rate is very close to
$$
(1-p)^k = \big(1 - e^{-kn/m}\big)^k .
$$
This is Bloom's estimate; it treats the probed bits as independent, which they are not, and it is slightly **below** the true rate, which even exceeds $\big(1 - (1-\frac1m)^{kn}\big)^k$ for $k\ge 2$. The rate grows with $n$ and falls with $m$.

**The best number of hash functions.** Too few hash functions test too few bits; too many fill the array with 1s. With $p = e^{-kn/m}$, that is $k = -(m/n)\ln p$,
$$
\ln\big((1-p)^k\big) = k\ln(1-p) = -\frac mn\,\ln p\,\ln(1-p),
$$
and $\ln p\ln(1-p)$, symmetric under $p\leftrightarrow 1-p$, is largest at $p = 1/2$.

> [!key] Optimal Bloom filters
> For given $n$ and $m$, the false-positive estimate is minimized by $k = (m/n)\ln 2$ hash functions — exactly when half the bits are 0 — and then equals
> $$
> \Big(\frac12\Big)^{(m/n)\ln 2}\approx(0.61850)^{m/n}.
> $$
> So a false-positive rate $\delta$ needs about $m = n\lg(1/\delta)/\ln 2\approx 1.44\,n\lg(1/\delta) = \Theta(n\log(1/\delta))$ bits and $k = \lceil\lg(1/\delta)\rceil$ hash functions.

In practice $k$ must be an integer, so the optimum is only approached. The note's sizing rule $m = \lceil n\lg(1/\delta)/\ln 2\rceil$ with $k = \lceil\lg(1/\delta)\rceil$ meets $\delta$ exactly only when $\lg(1/\delta)$ is an integer; otherwise the estimate overshoots slightly — for $\delta = 1\%$, $9.59n$ bits and 7 functions give $1.004\%$, and no integer $k$ reaches $1\%$ at that size. The note's examples, which round the space up: $10n$ bits and 7 hash functions give $0.82\%$ (the exact rate for $n = 1000$ is also $0.82\%$, and simulated filters agree); $32n$ bits — one 32-bit word per item — and 22 hash functions give $2.1\cdot 10^{-7}$.

> [!trap] Bloom-filter traps
> - **Errors are one-sided**: "no" is always right, "maybe" can be wrong. A Bloom filter cannot delete an item (clearing its bits could create false negatives) or list its items.
> - **The false-positive rate is for one query $y\notin X$, over the random hash functions**; a query asked twice gets the same answer both times.
> - **More hash functions is not better**: beyond $(m/n)\ln 2$ the rate rises again.

The note ends the section with an unanswered placeholder about extensions (counting filters for deletions, Bloomier filters for key–value pairs).

## 6.3 Streaming algorithms

A **data stream** is a huge sequence $S$ of items from a universe $\mathcal U$, available for a single front-to-back pass: the packets through a router, the searches at a search engine, the bids on a stock exchange. There is too much data to store, and it arrives too fast for complex computation. A **streaming algorithm** keeps a small summary and updates it as each item arrives:

```text
DoSomething(S):
    ⟨⟨initialize⟩⟩
    while S is not done
        x ← next item in S
        ⟨⟨do something fast with x⟩⟩
    return ⟨⟨something⟩⟩
```

Ideally neither the time per item nor the space depends on the length of the stream — viewed as ordinary algorithms, all streaming algorithms run in constant time. Even so, with randomization and a tolerance for error, interesting properties of the stream can be estimated.

## 6.4 The count-min sketch

**Problem:** at any moment, estimate the number $f_x$ of occurrences so far of an arbitrary item $x$. The **count-min sketch** (Graham Cormode and S. Muthu Muthukrishnan, 2005) is a Bloom filter with counters: a $d\times w$ array $\mathit{Count}$ of counters, initially 0, and $d$ hash functions $h_1,\ldots,h_d\colon\mathcal U\to[w]$, drawn independently from a 2-uniform family. (The note calls it a "$w\times d$ array" with $h_i\colon\mathcal U\to[m]$; its pseudocode indexes rows by $i\le d$ and columns by $h_i(x)$, so the range is $[w]$.)

```text
CMIncrement(x):                         CMEstimate(x):
    for i ← 1 to d                          est ← ∞
        j ← h_i(x)                          for i ← 1 to d
        Count[i, j] ← Count[i, j] + 1           j ← h_i(x)
                                                est ← min{est, Count[i, j]}
                                            return est
```

> [!key] The count-min guarantee
> Let $N$ be the length of the stream so far and $\hat f_x$ the value of $\textsf{CMEstimate}(x)$. With $w = \lceil e/\varepsilon\rceil$ and $d = \lceil\ln(1/\delta)\rceil$:
> - $\hat f_x\ge f_x$, always;
> - $\Pr\big[\hat f_x > f_x + \varepsilon N\big]\le\delta$, for every fixed stream and every fixed item $x$; the probability is over the choice of the hash functions only.
>
> The sketch has $O(\frac1\varepsilon\log\frac1\delta)$ counters, and each update or query takes $O(\log\frac1\delta)$ time. The error is **additive**: an estimate of a rare item may be many times its true count.

> [!proof]- Proof (click to expand)
> For $y\ne x$ let $X_{i,x,y} = [h_i(x) = h_i(y)]$, and let $X_{i,x} = \sum_{y\ne x}X_{i,x,y}\,f_y$ be the number of arrivals of other items that land in $x$'s counter in row $i$. Then $\mathit{Count}[i, h_i(x)] = f_x + X_{i,x}\ge f_x$ in every row, so $\hat f_x\ge f_x$. A 2-uniform family is universal, so $\operatorname{E}[X_{i,x,y}] = 1/w$, and by linearity $\operatorname{E}[X_{i,x}] = \frac1w\sum_{y\ne x}f_y\le N/w$. The estimate exceeds $f_x + \varepsilon N$ only if **every** row has $X_{i,x} > \varepsilon N$; the rows use independent hash functions, and by Markov's inequality each such event has probability at most $\operatorname{E}[X_{1,x}]/(\varepsilon N)\le 1/(w\varepsilon)$. Hence
> $$
> \Pr\big[\hat f_x > f_x + \varepsilon N\big] = \Pr\big[X_{1,x} > \varepsilon N\big]^d\le\Big(\frac1{w\varepsilon}\Big)^d\le e^{-d}\le\delta. \qquad\square
> $$
> (The note writes its last line as $\Pr[\hat a_x > a_x + \varepsilon N]$, the notation of Cormode and Muthukrishnan's paper. Its claim "$<\delta$" is also true, although its displayed chain shows only $\le$: Markov's inequality is strict for the event $X_{1,x} > \varepsilon N$ whenever that event has positive probability.)

**Example.** For $\varepsilon = 0.01$ and $\delta = 0.001$: $w = 272$, $d = 7$, $1904$ counters, whatever the length of the stream; each estimate is within $N/100$ of the truth with probability at least $0.999$. Markov's inequality is generous: simulating $\varepsilon = \delta = 0.05$ on skewed streams, 4 of 30,000 estimates exceeded $f_x + \varepsilon N$.

> [!trap] Count-min traps
> - **The guarantee is per query.** For many items at once, multiply $\delta$ by the number of items (union bound).
> - **The stream must not depend on the hash functions** — an adversary who could watch the estimates could choose items that collide.

## 6.5 Estimating distinct items

Unfinished: the note has only a to-do list — the AMS estimator $2^{z+1/2}$, with $z$ the largest number of trailing zeros among the items' hash values, or the Flajolet–Martin/Bar-Yossef et al. estimator of the exercises; median amplification; higher moments.

Exercise 2 (after Bar-Yossef, Jayram, Kumar, Sivakumar and Trevisan, 2002) estimates the number $n$ of **distinct** items: choose $h\colon\mathcal U\to[m]$ from a 2-uniform family, $m$ large, keep only $\bar h = \min\{h(x)\mid x\in S\}$, and output $\tilde n = m/\bar h$; the idea is that $n$ random points in $[m]$ have minimum about $m/n$, and repeats do not change the minimum. The exercise asks for proofs that $\Pr[\tilde n > (1+\varepsilon)n]\le 1/(1+\varepsilon)$ and $\Pr[\tilde n < (1-\varepsilon)n]\le 1-\varepsilon$, then sharpens the estimator with the $k$th smallest hash value and the median of $d$ copies. (The bounds need the exercise's "$m$ large": the minimum $\bar h$ is 0 — no finite estimate — with probability up to $n/m$, which breaks the first bound when $m\approx 4n$ and, barely, even for a single item with $m = p = 1009$: $\Pr[\tilde n > 1.9n] = 532/1009 > 1/1.9$.) ## Summary

- Fast but possibly wrong: fix an error probability $\delta$ in advance; "with high probability" means $\delta < 1/n^c$.
- Bloom filter: $m$ bits, $k$ independent ideal hash functions; insert sets $k$ bits, query tests them. No false negatives; false-positive rate $\approx(1 - e^{-kn/m})^k$, a slight underestimate.
- Best $k = (m/n)\ln 2$ (half the bits set), rate $(1/2)^k\approx 0.6185^{m/n}$; rate $\delta$ costs $\approx 1.44\lg(1/\delta)$ bits per item and $\lceil\lg(1/\delta)\rceil$ hash functions ($10n$ bits and 7 functions: $0.82\%$).
- Streaming: one pass, per-item time and memory independent of the stream length.
- Count-min sketch: $d = \lceil\ln(1/\delta)\rceil$ rows of $w = \lceil e/\varepsilon\rceil$ counters; estimate = minimum over the rows; never too small, and more than $\varepsilon N$ too large with probability $\le\delta$ (universality, linearity of expectation, Markov, independent rows).
- Distinct items: unfinished in the note; an exercise estimates $n$ by $m/\min h(x)$ and improves it with the $k$th smallest value and medians.
- The note ends with 2 exercises (reservoir sampling: one uniformly random item, or $k$ of them, from a stream of unknown length; the distinct-items estimator above).
